# 自动订阅源同步系统实施计划

> 状态：历史 Markdown 方案；实现状态与偏差见 `docs/source-sync-implementation-notes.md`
>
> 范围：YouTube Channel、YouTube Playlist、X Likes、X Lists
>
> 本文是后续实现与验收依据。浏览器扩展继续负责手动收藏；本文设计的是独立的本地自动订阅源系统。

## 1. 目标

在本机提供一个独立 Dashboard，用来：

1. 添加、暂停和管理自动订阅源；
2. 定时发现 YouTube 和 X 的新增内容；
3. 展示来源中的内容及其未同步、排队中、处理中、已同步、失败状态；
4. 支持单条、勾选多条和按筛选结果批量同步；
5. 对已同步内容全局去重，不重复生成；
6. 复用现有 Podcast 的字幕和分层产物生成能力；
7. 对 X Likes 全量整理，对 X Lists 先做价值判定；
8. 通过每页 20 条和水位重合保证不漏 Likes，同时避免大批量 X 请求。

## 2. 明确不做

- 不把自动发现内容写入浏览器扩展 outbox；
- 不把新 Dashboard 塞进 Chrome 扩展；
- 不复制第二套 Podcast 字幕或文章生成代码；
- 不让 YouTube 字幕失败升级成 Chrome、OpenCLI Browser 或 Cookie 自动化；
- 不下载 YouTube 音视频做语音转写；
- 不在第一版训练推荐模型或建设自学习系统；
- 不对 X 执行点赞、转发、发帖、关注等写操作；
- 不通过提高 OpenCLI `--limit` 一次读取几百或上千条 Likes。

## 3. 与手动收藏系统的关系

```text
手动收藏
  → Chrome 扩展 Dashboard
  → chrome.storage + extension outbox/inbox
  → 手动 Processing Flow

自动订阅源
  → 本地 Source Sync Dashboard
  → 独立 SQLite + 独立任务队列
  → Source Sync Worker
```

两者只共享内容处理 seam：

```text
YouTube URL → Podcast Processor → TLDR + 1000 字总结 + 按需 7000 字总结 + 全文稿
Tweet 数据  → Tweet Organizer   → 中文整理稿
```

自动系统不得修改扩展拥有的 outbox。两套系统拥有各自的发现与排队状态，但共享 Processor 必须幂等，避免同一内容从两个入口重复生成。

## 4. 领域语言

实施时把最终术语补入根目录 `CONTEXT.md`，代码中不另造同义词。

- **Monitored Source（监控来源）**：用户接入并由系统扫描的来源。类型为 `youtube_channel`、`youtube_playlist`、`x_likes`、`x_list`。
- **Content Item（内容实体）**：跨来源去重后的全局内容。YouTube 按 `video_id`，X 按 `tweet_id` 标识。
- **Source Relationship（来源关系）**：内容与来源的关系，状态为 `present | removed | unavailable`。
- **Discovery State（发现状态）**：一次扫描是否完整、停止原因、水位、页数、错误和时间；不表示内容是否已处理。
- **Sync Job（同步任务）**：对一个 Content Item 执行指定 Processor 的持久任务。
- **Collection Policy（收集策略）**：来源发现内容后是否自动入队的规则。
- **Value Decision（价值判定）**：X List 的 `collect | review | noise` 判断。
- **Organized Tweet（已整理 Tweet）**：Tweet Organizer 已成功保存的结果。中文不翻译但仍属于已整理。

同步状态：

```text
not_synced → queued → syncing → synced
                    ↘ failed → queued
```

## 5. 总体架构

第一版使用一个本地 Python 应用，不引入 Web 框架、前端框架或外部数据库：

```text
launchd / Dashboard 手动触发
             ↓
      Source Sync App
      ├─ Source Adapters
      │  ├─ YouTube Channel（yt-dlp）
      │  ├─ YouTube Playlist（yt-dlp）
      │  ├─ X Likes Page（OpenCLI，20 条）
      │  └─ X List Page（OpenCLI，20 条）
      ├─ Source Registry（SQLite）
      ├─ Collection Policy
      ├─ Job Worker
      └─ Dashboard（127.0.0.1 + 原生 HTML/CSS/JS）
             ↓
      Shared Processors
      ├─ Podcast Processor
      └─ Tweet Organizer
```

默认数据位置：

```text
~/.info-collector/source-sync/source-sync.db
~/.info-collector/source-sync/logs/
~/.info-collector/source-sync/status.json
```

SQLite 使用 Python 标准库 `sqlite3`，负责唯一约束、事务、批量筛选和 Dashboard 查询。

## 6. 模块 Interface

### Source Registry

```text
add_source(url, initial_policy) → source
record_scan(source_id, page_or_snapshot) → discovery_result
enqueue(content_keys) → {queued, skipped_synced, skipped_active}
claim_jobs(limit) → jobs
finish_job(job_id, result) → status
```

SQLite 表、事务和状态迁移隐藏在模块内部。

### Source Adapter

```text
inspect(url) → source_preview
scan(source, checkpoint) → scan_page_or_snapshot
```

返回稳定内容 ID、规范化 URL、标题或正文、作者或频道、发布时间、来源顺序、下一页 checkpoint 和是否到达末尾。

### Podcast Processor

从 `flows/podcast-bookmarks.py` 抽出队列无关的共享 Interface：

```text
lookup(canonical_youtube_url) → not_synced | synced + output_paths
process(canonical_youtube_url, metadata) → result
```

`process()` 必须先检查有效 `result.json` 和三个产物文件；已有产物时直接返回。

### Tweet Organizer

```text
process(tweet_record) → organized_result
```

它接收 OpenCLI 已取得的结构化 Tweet，不重新访问 X 页面。Pi 负责语言判断、翻译、中文标题和整理；Python 负责输入输出、状态与结果校验。

### Value Evaluator

```text
evaluate(list_policy, tweet_records[]) → value_decisions[]
```

按批次调用 Pi 并返回结构化 JSON。扫描器不做语义判断，Value Evaluator 不负责入队。

## 7. 最小数据模型

### `sources`

保存来源类型、规范化 URL、外部 ID、名称、启用状态、`auto_sync_new`、首次同步数量、来源设置、上次扫描状态和错误。

### `content_items`

主键 `content_key`：

```text
youtube:<video_id>
x:<tweet_id>
```

同时保存规范化 URL、标题或正文、作者、发布时间、语言和平台元数据。

### `source_relationships`

保存 `source_id + content_key`、`first_seen_at`、`last_seen_at`、`position` 和 `present | removed | unavailable`。唯一约束为 `(source_id, content_key)`。

### `value_decisions`

保存四项分数、总分、`collect | review | noise`、原因码、解释、置信度和用户覆盖记录。

### `sync_jobs`

保存 processor、状态、触发来源 `auto | user | initial_import`、尝试次数、错误、时间和结果。相同 `(content_key, processor)` 的 `synced`、`queued`、`syncing` 不得重复入队；`failed` 可重试。

### `source_checkpoints`

保存 YouTube 快照、X overlap IDs、进行中的 cursor 和上次完整扫描信息。

## 8. 来源策略

| 来源 | 发现方式 | 默认策略 | 处理器 |
|---|---|---|---|
| YouTube Channel | `yt-dlp` 扫 `/videos` 最近 N 条 | `auto_sync_new` | Podcast Processor |
| YouTube Playlist | `yt-dlp` 读取完整快照 | `auto_sync_new` | Podcast Processor |
| X Likes | OpenCLI 每页 20 条追到水位 | `always_collect` | Tweet Organizer |
| X List | OpenCLI 每页 20 条追到水位 | `value_filter` | Value Evaluator → Tweet Organizer |

优先级：

1. 用户手动同步覆盖自动策略；
2. 同一 Tweet 只要来自 Likes，就必须收集，即使它先前在 List 中被判为 noise；
3. 已 `synced` 的内容不因新增来源关系重复同步；
4. `removed` 只改变来源关系，不删除产物。

## 9. YouTube Channel

```bash
yt-dlp \
  --flat-playlist \
  --playlist-end 5 \
  --dump-json \
  'https://www.youtube.com/@LennysPodcast/videos'
```

规则：

- 使用 `/videos`，只监控长视频；
- 不使用会混入 Shorts 的 RSS 作为主来源；
- 使用 `video_id` 去重，URL 统一为 `https://www.youtube.com/watch?v=<id>`；
- 默认扫描最近 5 条，来源设置允许调整；
- 新 ID 建立来源关系，再按 `auto_sync_new` 决定是否入队。

已验证：`@LennysPodcast`，频道 ID `UC6t1O76G0jYXOAoYCm153dA`。

## 10. YouTube Playlist

```bash
yt-dlp \
  --flat-playlist \
  --dump-single-json \
  'https://www.youtube.com/playlist?list=PLOhHNjZItNnMm5tdW61JpnyxeYH5NDDx8'
```

规则：

- 从 watch + list URL 提取 Playlist ID，只保存规范化 Playlist URL；
- 每次扫描完整列表，不只看前 5 条；
- 新 ID 按策略入队；只有顺序变化则更新 `position`；
- 移除时关系改为 `removed`，重新加入时恢复 `present`；
- 已同步内容不重复生成；
- 私密或暂不可用内容标记 `unavailable`，后续继续检查。

已验证：Playlist `PLOhHNjZItNnMm5tdW61JpnyxeYH5NDDx8`，名称 `Training Data`，所属 `Sequoia Capital`。

## 11. YouTube 同步处理

新系统复用现有 Podcast 处理能力，不复制字幕解析、Pi prompt 或 `result.json` 校验。

当前正式字幕路径以 ADR 0007 为准：

```text
Firecrawl transcript
    ↓ 失败
yt-dlp 手动/自动字幕
    ↓ 失败
youtube-transcript-unavailable
```

约束：

- 两种字幕来源都失败时不启动 Pi；
- 不打开或控制 Chrome；
- 不使用 OpenCLI 获取 YouTube 字幕；
- 不读取浏览器 Cookie；
- 不下载音视频做语音转写；
- `source.md` 存在后才运行 `podcast-digest`；
- `result.json` 且 TLDR、1000 字总结、全文稿均存在才算 `synced`；全文稿去掉
  frontmatter 后的非空白正文字符数达到 7000 时还必须存在 7000 字总结。

## 12. X Likes：严格 20 条分页

当前命令：

```bash
opencli twitter likes Tenitsugunsmith --limit 20 -f json
```

现有 adapter 内部支持 cursor，但没有暴露 cursor，并且底层单次请求数量可能大于 20。实施前必须增加严格单页读取能力，不能用大 limit，也不能重复读取第一页。

拟议只读 Interface：

```bash
opencli twitter likes-page Tenitsugunsmith \
  --count 20 \
  --cursor '<cursor>' \
  -f json
```

```json
{
  "items": [],
  "next_cursor": "...",
  "exhausted": false
}
```

分页 adapter 的源码和测试保存在本仓库，由 setup 脚本安装成 OpenCLI 私有命令；不得直接修改全局 npm 包中的已安装文件。若 OpenCLI 上游以后提供等价单页 Interface，再删除本地 adapter。

要求：

- 每次 X 请求最多 20 条；
- 严格串行，不并发；
- 每页返回后立即事务落库；
- 页面之间使用保守间隔；
- 遇到 429、登录失效、验证挑战或其他异常立即停止；
- 同一次运行不快速重试风控类错误；
- 不使用 `--top-by-engagement`；
- adapter 只读，不增加 X 写操作。

### 水位算法

每次完整扫描保存最近 5 个已安全落库的 Tweet ID 作为 `overlap_ids`。停止条件是与上次完整扫描的已发现记录重合，而不是等待完成整理。

```text
读取一页 20 条
    ↓
事务保存内容和来源关系
    ↓
所有新 Likes 创建整理任务
    ↓
命中任意 overlap_id？
    ├─ 是：完整结束并更新 overlap_ids
    └─ 否：使用 next_cursor 读下一页 20 条
```

只有命中水位或 `exhausted=true` 才算完整。异常中止时：

- 保留已落库页面；
- 不更新完整扫描水位；
- 保存 `next_cursor` 和停止原因；
- Dashboard 显示 `incomplete`；
- 后续恢复前验证 cursor 是否仍有效。

第一次接入：先从现有整理产物导入可识别的 `tweet_id`；有历史记录时追到重合位置；没有历史记录时逐页读到历史末尾或安全中止。所有新发现 Likes 都进入整理队列，不做价值筛选。

`first_seen_at` 只是首次观察时间，可以近似点赞时间；原帖 `created_at` 单独保存，不得冒充点赞时间。

## 13. X Lists

```bash
opencli twitter list-tweets 2058340249626128801 --limit 20 -f json
```

List 同样使用每页 20 条、显式 cursor、逐页落库和水位重合，不用大 limit。可以与 Likes Page 共享分页和风控代码，但保留不同 endpoint 和解析器。

OpenCLI 返回的 Tweet、作者简介、引用 Tweet、媒体和外链卡片作为第一版 Value Evaluator 输入。缺少 Thread 或外链正文导致无法判断时进入 `review`，不得直接丢弃。

## 14. X List 价值判定

每个 List 配置主题和阈值：

```json
{
  "topics": ["AI 产品", "Agent", "开发工具"],
  "minimum_collect_score": 7,
  "auto_sync_accepted": true,
  "send_borderline_to_review": true
}
```

评分总分 10 分：

| 维度 | 分值 | 含义 |
|---|---:|---|
| 主题相关性 | 0–3 | 与该 List 关注主题的关系 |
| 信息增量 | 0–3 | 新事实、方法、数据、资源或独到分析 |
| 实用性 | 0–2 | 对研究、开发、决策或进一步阅读的帮助 |
| 证据与上下文 | 0–2 | 是否具体、完整并有数据、案例、链接或推理 |

默认：

```text
7–10 且相关性 ≥ 1 → collect
4–6                 → review
0–3                 → noise
```

原因码：

```text
social_chatter
contextless_reaction
pure_promotion
engagement_bait
repetition
off_topic
insufficient_context
```

`insufficient_context` 必须进入 review；互动量只作辅助；noise 仍保留；用户可以人工覆盖。第一版只保存纠正记录，不训练模型。X Lists 先运行影子模式，人工检查约 50–100 条后再开启自动收集。

## 15. Tweet Organizer

Likes 全部进入；List 中只有 `collect` 或用户手动选择的内容进入。

输入至少包括 Tweet ID、URL、正文、作者、简介、发布时间、引用 Tweet、外链卡片、媒体和来源关系。

输出规则：

- 中文：整理原文，不翻译；
- 英文：保留原文并翻译成中文；
- 中英混合：只翻译英文部分；
- 保留引用、外链卡片和媒体 URL；
- 生成简短中文标题、必要标签和来源元数据；
- 不扩写成原文没有表达的长文章。

分别记录：

```text
sync_status = synced
translation_status = not_needed | translated | partially_translated
```

Obsidian 输出目录、文件命名、frontmatter 和是否建立 Base 在实施前确认。

## 16. Dashboard

Dashboard 只监听 `127.0.0.1`。

来源列表显示名称、类型、启用状态、自动同步策略、内容数量、各同步状态数量、上次扫描、扫描页数、停止原因、水位是否接上和预计下次扫描。

来源操作：添加、暂停/恢复、立即扫描、编辑策略、查看内容、删除监控关系。删除来源不删除内容和产物。

内容表支持：

- 按来源、平台、同步状态、价值判定、语言和关键词筛选；
- 单条或勾选多条同步；
- 同步当前筛选结果中的未同步内容；
- 对 review 批量 collect/noise；
- 重试 failed；
- 查看判定理由、失败原因和产物路径。

批量操作返回：

```text
已加入 4 条
跳过已同步 2 条
跳过排队中/处理中 1 条
```

## 17. 添加来源与首次同步

1. 粘贴频道、Playlist、X Likes 或 X List URL；
2. `inspect()` 识别类型并规范化；
3. 展示名称、类型、数量或最近内容预览；
4. 确认自动扫描和自动同步策略；
5. 选择首次同步范围；
6. 保存来源、建立初始关系并创建任务。

YouTube 选项：

```text
只建立监控，不同步历史
同步最新 5 条（默认）
同步最新 N 条
同步全部
```

频道按 `/videos` 顺序；Playlist 没有可靠加入时间，界面写“当前列表前 N 条”，不能称“最近加入 N 条”。

X Likes 首次接入不以固定条数作为完成条件，而是逐页追到历史重合或历史末尾。X List 可设置初始扫描范围，并默认进入影子判定模式。

## 18. 调度与失败

- launchd 定时触发扫描和 Worker；
- Dashboard 手动操作调用同一模块 Interface；
- 同一来源同时最多一个扫描任务；
- X 请求严格串行；
- Podcast Worker 第一版每次最多处理 2 条；
- Tweet Organizer 第一版串行；
- 超时的 syncing 任务可恢复为 queued；
- 429、认证和风控错误暂停来源，同次运行不快速重试；
- 扫描失败和处理失败分开显示。

## 19. 实施阶段

按纵向切片推进，每个阶段结束都能实际使用。

### 阶段 1：Dashboard + YouTube Channel

实现 SQLite、Dashboard、来源管理、Channel scan、内容表、批量入队、幂等 Podcast Processor 和单视频端到端处理。

验收：添加 Lenny's Podcast 后看到最近 5 个长视频；已有产物显示已同步；批量同步只处理未同步内容；成功后显示三个产物路径；重复点击不重复生成。

### 阶段 2：YouTube Playlist + 首次设置

实现 Playlist 规范化、完整快照、关系状态、首次同步数量和 `auto_sync_new`。

验收：Training Data 的完整基线可展示；模拟新增、移除和重排时状态正确；当前前 N 条只入队 N 条；移除或重加不重复处理。

### 阶段 3：X Likes 安全分页 + 全量整理

实现严格单页 20 条的 Likes Page adapter、cursor、overlap IDs、逐页事务、扫描进度、Tweet Organizer 和语言规则。

验收：每次底层请求不超过 20；多页数据在重合处停止；中途失败不前移水位；新 Likes 全部入队；重复 Tweet 不重复整理；中英文样本走正确路径。

### 阶段 4：X Lists + 价值判定

实现 List Page adapter、List 主题和阈值、Value Evaluator、collect/review/noise、人工覆盖和 Likes 优先级。

验收：固定样本输出稳定结构；上下文不足进入 review；noise 可见但不自动入队；后来出现在 Likes 的 noise 会入队；可导出 50–100 条影子样本校准。

### 阶段 5：调度与运行维护

实现 launchd、锁、风控暂停、日志、备份、SQLite 完整性检查、README 和 implementation-notes。

验收：登录后调度恢复；重启不丢任务、不重复处理；X 认证失败不快速重试；安装卸载不影响现有扩展系统。

## 20. 测试策略

单元测试覆盖 URL 规范化、Content Key、SQLite 状态迁移、Playlist diff、X overlap、单页 20 条、Value Decision 阈值、Likes 优先级和批量去重。

集成测试使用临时 SQLite 和假 Adapter/Processor，覆盖添加来源到完成任务、扫描中断不前移水位、Worker 崩溃恢复、重复发现不重复入队以及 Dashboard 与数据库一致。

只读现场验证来源：

- Lenny's Podcast Channel；
- Training Data Playlist；
- `Tenitsugunsmith` Likes；
- List `2058340249626128801`。

所有 X 现场验证只读、串行、每页 20 条，异常立即停止。

## 21. 实施前确认项

- 自动扫描频率；
- X 单页之间的保守间隔；
- Likes 首次历史回溯的暂停/恢复节奏；
- Tweet 整理稿的 Obsidian 目录、文件名和 frontmatter；
- 是否为 Tweet 建独立 Obsidian Base；
- 各 X List 的主题和初始阈值；
- 本地 Dashboard 的正式名称。

这些选项不改变总体架构，在对应切片开始前确认即可。

## 22. 完成定义

- 自动系统与浏览器扩展队列完全独立；
- Dashboard 管理四类来源；
- YouTube Channel/Playlist 可以发现、选择和自动同步；
- X Likes 每页最多 20 条并追到水位，所有新 Likes 都进入整理队列；
- X Lists 能输出 collect/review/noise 并支持人工覆盖；
- 中文 Tweet 不翻译，英文 Tweet 翻译成中文；
- 自动触发和手动批量触发都全局去重；
- YouTube 只走 Firecrawl → yt-dlp → 明确失败的安全字幕路径；
- 扫描不完整、失败和风控暂停在 Dashboard 中可见；
- 测试、安装脚本、README 和 implementation-notes 与实际行为一致。
