Podcast 流实现计划

目标是在现有 Info Collector 队列体系里新增 podcast processing type： 从网页文稿或 YouTube transcript 生成三个 Obsidian 文件： TLDR、深度总结、全文稿。本文先列最可能需要你调整的产品与数据决策， 机械实现步骤放在底部。

设计依据： podcast-design.md、 ADR 0005、 ADR 0006。

默认路径 网页用 Defuddle；YouTube 用 Firecrawl，再 yt-dlp，最后 Chrome Transcript UI。
生成职责 翻译、清理、标题中文化、摘要、写 Obsidian 全部交给 pi -p skill。
v1 不做 不转音频，不同步 Notion，不依赖 OpenCLI，不默认读主账号 Chrome cookies。

最可能要调的决策

1. 数据模型：把“来源类型”和“获取机制”拆开

推荐保留两个字段：transcript_source 表示文本本身是什么， transcript_provider 表示怎么拿到。Firecrawl 可能返回创作者字幕， 也可能返回自动字幕，但它不稳定暴露 kind，所以不能把 provider 当 source。

字段 推荐值 为什么你可能会改
transcript_source webpage_transcript / youtube_manual_caption / youtube_auto_caption / youtube_unknown_caption 如果你希望 Firecrawl 的结果强行按 manual/auto 分类，需要另做比对或探测。
transcript_provider defuddle / firecrawl_youtube / yt_dlp 如果未来接 ScrapeCreators、Apify 或自建服务，这里会扩展。
caption_kind manual / auto / unknown 如果你不关心可信度，可以删掉；但保留它能解释全文稿质量差异。
source_reliability edited / manual_caption / auto_caption / unknown_caption 如果 Obsidian 里不需要筛选质量，可以只保留 source/provider。

2. 新接口：Podcast workdir 是 flow 和 Pi 的唯一边界

flow 不直接调用 LLM，也不写最终 Obsidian 内容。它只准备 source.md 和 meta.json，然后调用 pi -p。Pi 写 result.json，flow 只校验这个文件。 

work/podcast/<articleKeyHash>/
  source.md     # transcript 原文，可能是中文，也可能是英文
  meta.json     # URL、来源元数据、输出目录、resultFile
  result.json   # Pi 写入，flow 的唯一成功信号

推荐的 result.json 成功形态： 

{
  "status": "ok",
  "tldrFile": "...",
  "deepSummaryFile": "...",
  "transcriptFile": "..."
}

3. 用户可见：新增“保存为播客”，并保持三文件输出

界面/产物 推荐方案 可调整点
Popup 新增 保存为播客 按钮，只创建 podcast job，不创建 translate job。 也可以只在 Dashboard 里手动加入队列；但 popup 能从根上避免误翻译竞态。
Dashboard 无当前类型 job 时显示 加入队列；失败原因进 chip title。 如果你想少改 UI，Dashboard 加入队列可以 P1；popup 是 P0。
Obsidian 播客收集/<中文标题>（TLDR）.md、（深度总结）.md、（全文稿）.md 如果你嫌文件多，可以改成两个文件，但这会违背当前“三件套”决策。
Notion v1 不同步。 需要新数据库属性集；等本地 Obsidian 跑稳再做。

4. YouTube provider 顺序

推荐顺序是 Firecrawl → yt-dlp。拿不到字幕就失败，不打开或控制用户 Chrome。

  1. Firecrawl：标准 watch URL，抽 ## Transcript 后正文，标 youtube_unknown_caption。
  2. yt-dlp：只下载字幕，优先 --write-subs，再 --write-auto-subs。
  3. 失败：写入 youtube-transcript-unavailable，等待用户提供有字幕或已有文稿的来源。

被排除在 v1 主路径外：Chrome UI、summarize 的 youtubei/get_transcript、 captionTracks.baseUrl、OpenCLI YouTube adapter、音频转写。

新类型接口

Processing Type

{
  "id": "podcast",
  "label": "播客",
  "autoEnroll": false
}

Completion Report meta

{
  "tldrFile": "...",
  "deepSummaryFile": "...",
  "transcriptFile": "...",
  "transcriptSource": "webpage_transcript",
  "transcriptProvider": "defuddle",
  "captionKind": null,
  "transcriptLanguage": "zh",
  "sourceReliability": "edited"
}

Pi skill 输入

Prompt 只传 workdir 路径。skill 自己读 source.md 和 meta.json。如果 source.md 不存在且 `source.md` 缺失时直接失败；skill 不走 Chrome UI 兜底，也不使用 OpenCLI。

实施阶段

阶段 1

Podcast flow 骨架与解析器

  • 新建 flows/podcast-bookmarks.py，复用 translate flow 的锁、outbox/inbox/status/reported-state 模式。
  • 实现非 YouTube 的 Defuddle 路径：正文够长就写 source.md，过短则查 YouTube embed。
  • 实现 YouTube URL 标准化、Firecrawl provider、yt-dlp provider、json3/VTT 解析。
  • 只做确定性处理；不在 Python 里翻译、总结或改写。
阶段 2

podcast-digest skill

  • 创建 skills/podcast-digest/SKILL.md。
  • 负责标题中文化、正文清理、英文全文翻译、TLDR、深度总结、全文稿写入。
  • 实现 Chrome Transcript UI fallback：绑定现有 Chrome，不杀进程，不创建临时 profile。
  • 写 result.json，失败也写结构化 error。
阶段 3

扩展用户入口

  • Popup 增加 保存为播客，调用 saveTab({ types: ["podcast"] })。
  • saveTab 接受可选 types 覆盖 autoEnroll 类型集，并校验类型已注册。
  • Dashboard 对没有当前类型 job 的记录显示 加入队列。
阶段 4

安装与注册

  • 新增 scripts/setup-pi-podcast-flow.sh，复制 flow 和 skill。
  • 新增 templates/com.pi.podcast-bookmarks.plist。
  • 在 flows registry 中加入 podcast command。
  • Dashboard 手工注册 processing type：podcast / 播客 / autoEnroll=false。
阶段 5

验证

  • 单元测试：Defuddle 长文、短文含 YouTube、短文无 transcript、Firecrawl 403 拒绝、yt-dlp manual 优先、json3/VTT 解析。
  • 扩展测试：saveTab(types) 覆盖 autoEnroll；Dashboard setJobStatus 可为缺失 job 创建 pending。
  • 真实链路：一篇微信样本跑完整三件套；一篇 YouTube 只跑 transcript provider smoke，不下载音视频。

验收标准

  • 保存播客 URL 后，不产生 translate job。
  • 非 YouTube 成熟文稿能通过 Defuddle 进入 Pi，产出三个 Obsidian 文件。
  • YouTube 自动字幕和创作者字幕至少各有一个 provider smoke 通过。
  • 所有 done 报告都包含三件套文件路径和 transcript 元数据。
  • 失败时 Dashboard 能看到明确错误码：no-existing-transcript、youtube-transcript-unavailable 或 pi-failed。
